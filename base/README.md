# base/ — сохранение базы (серверная логика)

Rust-модуль TUI-приложения `kot-tas`, по аналогии с `stones/`. Перехватывает
исходящую дельту редактора (`ChangeDungeonObject`, поле 30 обёртки
`KTProtocol::Request`) и сдвигает координаты перемещаемого объекта: клиент
показывает одно, сервер получает другое.

**Статус:** проверено на 2.84.2 x86_64 (Waydroid). AOB-сигнатуры находят все
четыре функции уникально, контракт агента (`moduleBase`/`installHooks`/
`setCells`/`setPixels`/`enable`/`status`/`unhookAll`) проверен на живой игре.

## Файлы

| файл | что |
|---|---|
| `config.rs` | `BaseConfig` (+ `Direction`): разбор `config.yaml`, перевод клеток в пиксели, юнит-тесты |
| `mod.rs` | `BaseModule`: загрузка хука, `ScriptHandler`, RPC-обёртки, меню-команды (`HELP`) |
| `hook.js` | frida-агент: подмена в `Message::SerializeToArray`, сжатие макета в одну точку |
| `../memory/offsets.js` | секции `protocol`: AOB-сигнатуры, фолбэк-RVA, смещения обёртки, геометрия арены, `protocol.dungeon` (парсеры и смещения `Dungeon`) |

## Конфиг (`config.yaml`)

```yaml
base:
  enabled: false       # подменять сразу после загрузки модуля
  cells: 1             # сдвиг в клетках (0 — не двигать); клетка = 64 px
  dir: "left"          # left | right | up | down
  cell_px: 64          # размер клетки арены в пикселях
  # pixels: [-32, 0]   # альтернатива: точный сдвиг в пикселях (или {x: -32, y: 0})
```

Если задан `pixels`, `cells`/`dir` игнорируются.

## Меню TUI

```
base                     справка + текущее состояние
base cells <N> <dir>     сдвиг на N клеток: left | right | up | down
base px <dx> <dy>        сдвиг в пикселях (например: base px -32 0)
base on / base off       включить / выключить подмену
base reset [x y]         все объекты базы в одну точку (по умолчанию 448 224)
base reset off           снять режим reset
base status              что применяется сейчас (состояние хоста и агента)
base stop                снять хуки
```

## Как это работает

1. `BaseModule::ensure_loaded()` читает `hook.js`, прогоняет через
   `memory::prepend_layout` (подкладывает `memory/offsets.js` и проверяет
   `Process.arch`) и создаёт скрипт.
2. Агент находит `libthieves.so`, разрешает функции по AOB-сигнатурам
   (скан только по `r-x`-диапазонам модуля, с фолбэком на RVA) и ставит хук на
   `Message::SerializeToArray`.
3. На выходе из хука: проверяется, что это `KTProtocol::Request` с заполненным
   полем 30, в байтах ищется подсообщение `{f1: слот, f2: x, f3: y}` и
   переписываются `x`/`y` с сохранением длины varint'а — размер пакета не меняется.
4. Каждый патч печатается в консоль TUI:
   `[base] #1 слот=3 x 320 -> 256  y 192 -> 192  (offset -64/0)`

## Reset: все объекты базы в одну точку

`base reset` — локальная правка: координаты объектов меняются в памяти
клиента, на сервер не уходит ничего (черновик на сервере остаётся прежним).

1. Хук встаёт на `Dungeon::MergePartialFromCodedStream` (RVA `0x105c7c0`). У
   protobuf-парсеров общий пролог, поэтому AOB-сигнатура не уникальна — адрес
   берётся по RVA, а пролог сверяется перед установкой хука (с повторами: сразу
   после старта игры страницы кода готовы не instantly). При апдейте игры модуль
   скажет об этом, а не хукнет постороннюю функцию; состояние видно в
   `base status` как `reset.hooked`.
2. Режим держится до `base reset off`: на каждом разборе макета у объектов из
   `f1` (`count` +0x20, `rep` +0x28) переписываются `x`/`y` (+0x18/+0x1c) на
   заданную точку. Пишутся только записи, похожие на `Dungeon_Obstacle`
   (тип 1..255, слот 0..64, указатель читается), остальные считаются в `skipped`.
3. Каждая правка печатается в консоль TUI:
   `[base] reset: 10 объектов -> (448, 224) [layout] всего 10`.

Что видно на практике (проверено на живой игре 2.84.2): объекты съезжаются к
заданной точке, но клиент раскладывает их по соседним клеткам, чтобы они не
перекрывались, — получается плотная группа, а не идеальная стопка.

Уровень в памяти клиента — отдельная плоскость: сообщение правится до спавна
объектов, поэтому трогать уже созданные объекты сцены этот режим не умеет.

## Перезапуск игры

Перезапуск игры рвёт frida-сессию, поэтому `kot-tas` держит её как сменяемую:
при выходе процесса он пишет `INFO main: соединение с игрой потеряно` и ждёт
запуск (Ctrl+C — выход), а после появления процесса подключается заново. Меню
при этом не падает: во время ожидания команды сессия проверяется каждые 50 мс,
так что смерть игры видна сразу, а не на следующей команде.

Вместе с хуками восстанавливается последнее состояние `base`: смещение из
`base cells`/`base px`, флаг `base on/off` и режим `base reset` с точкой.
В логе это видно как `INFO main: base восстановлен: BaseSnapshot { … }`.
Остальные модули (TAS, catacombs, stones) грузятся заново пустыми — их
состояние после рестарта игры не сохраняется.

## Ограничения (проверены опытом)

* Дельта попадает в **черновик** базы. Игроки, заходящие на базу, получают
  только зафиксированное состояние — то есть после успешного `ConfirmDungeon`,
  а он проверяет, что ваш реплей физически проходит в новой раскладке.
* Сдвиг объекта, стоящего на вашем маршруте, ломает подтверждение («реплей
  расходится с раскладкой»).
* Мгновенную серверную ошибку у другого игрока через данные базы получить
  нельзя: типы объектов и границы параметров валидируются, координаты клиент и
  симуляция интерпретируют одинаково, а метку времени сервер сверяет со своими
  часами.
* Reset меняет только то, что видит и считает мой клиент. Сервер по-прежнему
  играет сохранённую раскладку, поэтому сжатая база не сохраняется и не делает
  забег другого игрока легче: результат забега сверяется на сервере по
  настоящей раскладке.
* Правка макета не трогает уже созданные объекты уровня: клиент рисует сцену из
  живых объектов, а не из сообщения. Чтобы увидеть результат, нужен новый
  разбор раскладки (перезаход в базу).

Полный разбор протокола: `../analysis/report/DUNGEON_SAVE_FLOW.md`,
структура пакета сохранения: `../analysis/report/SAVE_PACKET_FULL.md`.
