# Реплей: формат и логика

Реплей — один прогон уровня: шапка, скриншот базы, раскладка ловушек, план
прыжков и эталон состояния персонажа. Файл — Markdown, картинка — в общем
каталоге `replays/images`.

```
replays/
  images/                     <- общий каталог кадров
    20261128-155103(1).png
    20261128-160210(2).png
  199477120/                  <- seed базы (Dungeon.f5)
    20261128-155103(1).md     <- вариант 1 прохождения
    20261128-160210(2).md     <- вариант 2 того же уровня
```

Один и тот же уровень (скелет + раскладка) можно пройти по-разному, поэтому у
файла есть номер варианта: он в имени `<время>(N)` и в шапке `variant: N`.
Номер считается по паре (скелет, раскладка) при записи: следующий всегда
`max(существующие) + 1`, старые файлы без номера занимают слоты снизу.

Картинки вынесены в общий `replays/images`: иначе при каждом прогоне одной базы
в её папке появлялась ещё одна копия кадра. В файле ссылка относительная —
`../images/20261128-155103(1).png`.

## Почему не JSON

Прежний `logs/replay.json` держал два источника истины в одном файле: блок
`"""` со скриптом кадров и JSON-тело с `events`/`body_frames`/`timeline_ns`.
При расхождении код печатал WARN и молча выбирал шапку, отключая сверку
состояния; поиск JSON начинался с первого `{` в файле, поэтому числа таймлайна
однажды стали прыжками. Теперь источник у каждого факта один, а расхождение —
ошибка загрузки.

## Структура файла

````markdown
# base 199477120 — 2026-11-28T15:51:03Z

![base 199477120](../images/20261128-155103(1).png)

```yaml
schema: 1
base: 199477120
layout: 16f12745
fps: 60
tap_down_ms: 1
anchor: first_hero_update@2684
jumps: 27
created: 2026-11-28T15:51:03Z
screenshot: ../images/20261128-155103(1).png
```

## Раскладка базы

```yaml
traps:
  - { slot: 0, type: 1, x: 704, y: 498 }
  - { slot: 1, type: 2, x: 64, y: 99 }
  - { slot: 2, type: 11, x: 704, y: 256 }
```

## План прыжков (резерв, если блока state нет)

```frames
delta: true
+26
+14
loop 2 {
+35
}
```

Блок понимает две шкалы: кадры (`+26`) и миллисекунды (`+400ms`). Смешивать их в
одном блоке нельзя — это ошибка разбора. Миллисекундный план исполняется по
стенным часам от старта уровня и **не пересчитывается в кадры**; покадровый эталон
`state` к нему не относится и игнорируется.

## Эталон состояния на момент прыжка

```state
# frame px py ang vx vy av a0 b0 g80 g84
2709 434.5 120.25 0 2.2 0 0 0 0 1 0
2723 434.5 110.75 0 2.2 -3.1 0 0 0 0
```
````

### Поля шапки

| поле | смысл |
|---|---|
| `schema` | версия формата; чужая версия — отказ, без попыток угадать |
| `base` | `Dungeon.f5` — скелет базы: сколько ловушек и какая арена |
| `variant` | номер прохождения для пары (скелет, раскладка): 1, 2, 3… |
| `layout` | подпись раскладки: FNV-1a 32 по `slot/type/x/y` всех ловушек |
| `fps`, `tap_down_ms` | темп и длительность тапа на момент записи |
| `anchor` | `вид@кадр` — от него считаются дельты в блоке `frames` |
| `jumps` | число шагов плана; расхождение с блоками — предупреждение при чтении |
| `screenshot` | путь к PNG относительно файла (`../images/…`) |

### Почему `base` (f5) — не идентификатор базы

На живых данных `f5` общий у разных баз: 12 ответов сервера с
`f5 = 142614553` имели разное золото, разные уровни игроков и 7 разных наборов
типов ловушек, но всегда 11 ловушек. При этом повторный заход в одну и ту же
базу даёт побайтово ту же раскладку (проверено 5 из 5 на базе из 8 ловушек).
Поэтому `f5` — папка («база» в смысле скелета), а конкретную расстановку
различает `layout`.

## Правила разбора

1. Читаются только fenced-блоки с info-string `yaml`, `frames`, `state`.
   Проза, ссылка на картинку, base64 и чужие блоки (например ```json) не
   участвуют в разборе вообще.
2. Незакрытый fence — ошибка: файл обрезан.
3. Шапка — первый `yaml`-блок, содержащий `schema:`. Версия не совпала —
   отказ с текстом ошибки.
4. `frames`: `delta: true|false`, `+N`, `loop N { ... }`, комментарии `#` и `//`.
   Непонятная строка — ошибка, а не пропуск: опечатка в правленом руками файле
   не должна менять план.
5. `state`: ровно 11 колонок на строку, `frame` первым. **Первая строка —
   якорь** (тот же кадр, что в шапке), остальные — прыжки. Дробные значения —
   float32 в кратчайшей записи, чтобы сверка при `play` была битовой.
   Для миллисекундного плана блок `state` не применяется (в файле его лучше не
   оставлять, но разбор его просто игнорирует).
6. Приоритет: есть `state` — прыжки и эталон берутся из него, `frames` не
   используется. Есть оба и прыжки в них расходятся — файл противоречив, отказ.
   Строка якоря в `state` при сравнении с `frames` не учитывается: в скрипте
   дельты считаются от якоря, а не включают его.
7. Файл без прыжков и без шагов по времени — ошибка загрузки; такой прогон и не
   записывается.

## Запись (`record`)

- Скриншот базы делается в момент **первого обновления персонажа**
  (`first_hero_update`): уровень уже отрисован, но персонаж ещё в исходной
  точке. Съёмка — `adb -s <serial> exec-out screencap -p`, отдельным потоком,
  ничего в игру не пишется. Не получилось — `screenshot` в шапке не пишется,
  запись продолжается.
- Раскладка берётся **в момент загрузки уровня** — хук
  `GameScene2::loadDungeon(self, Dungeon*)` читает переданный объект, пока он
  ещё жив. Это единственный достоверный признак «какая база на экране»:
  - свой данж сервер присылает один раз при старте игры и больше не разбирает,
    поэтому «последний разбор `Dungeon`» — не то же самое, что текущая база;
  - клиент освобождает объект `Dungeon` после обработки ответа, поэтому читать
    его позже нельзя (`vtable_mismatch`);
  - уход с уровня (клиент отправил `SingleplayerAttackResult`/`MultiplayerAttackResult`)
    снимает текущую базу: пока новый уровень не собран, база считается неизвестной,
    и запись уходит в `seed0` с явным предупреждением, а не в чужую папку.
- Кадр снимается **один раз на пару (скелет, раскладка)**: второй вариант того же
  уровня — то же подземелье, поэтому он переиспользует существующий PNG (в консоли
  `кадр базы уже есть — переиспользую: …`). При ретенции общий кадр не удаляется,
  пока на него ссылается хоть один прогон.
- Переиспользование требует, чтобы раскладка была известна: TAS печатает её перед
  записью одной строкой (`(база: seed=… раскладка=…, ловушек …)`). Если там
  `раскладка не прочитана`, кадр сравнивать не с чем — файл уйдёт в `seed0`, и
  снимок будет новый. Причина обычно одна: уровень был собран до запуска TAS.
- Если раскладка прояснилась только к концу записи, кадр всё равно переиспользуется:
  дубль, снятый в этом прогоне, удаляется.
- В блок `state` попадают только кадры прыжков и якорь: сверка при `play` идёт
  по ним, полный покадровый лог в файле не нужен.
- Папка — `replays/<seed>/`, файл — `<YYYYmmdd-HHMMSS>(N).md`, кадр —
  `replays/images/<YYYYmmdd-HHMMSS>(N).png`. На базу хранятся последние
  `replays.keep_per_base` прогонов; запись и её кадр удаляются вместе.
- Прогон без единого прыжка не сохраняется: реплей хранит вызовы `jumpFn`, и файл
  из одного якоря нечего играть. `record` в этом случае печатает причину.

## Слежение за базой

Пока меню ждёт команду, TAS раз в 300 мс спрашивает модуль `base`, какая база
загружена. Как только уровень собран заново (счётчик `loads` изменился), ищется
запись с **тем же скелетом и той же подписью раскладки**:

```
┌─ под текущую базу 2 варианта: seed=17794082 раскладка=394ec424
│  1) 20261128-131153(1).md — 13 прыжков
│  2) 20261128-131246(2).md — 17 прыжков, БЛОКА STATE НЕТ!!!
└─ y — сыграть последний, y <номер> — конкретный, <номер> — показать png, dry-run — только план
```

Пометка `БЛОКА STATE НЕТ!!!` означает, что из файла убрали `state`: он играется по
резервному плану `frames`, прыжки те же, но сверять состояние персонажа не с чем.
Такой файл не отвергается — просто уровень доверия к нему ниже, и об этом
сообщается и в списке, и в самом `play`.

Вариантов может быть сколько угодно: один и тот же уровень проходят по-разному,
и все прохождения нужны. Позиции в списке — это порядок по номеру варианта;
`y 1` играет первый, `y` без номера — последний. `play` без аргумента по-прежнему
выбирает по живой раскладке (самый свежий файл).

Голый номер варианта (`1`, `2`, …) открывает **скриншот** этого прохождения
системным просмотрщиком; то же самое делают `png 2`, `open 2`, `pic 2`. Программа
берётся из `replays.viewer` (по умолчанию `xdg-open`), процесс отвязан — консоль
не ждёт закрытия окна.

Предложение обновляется **и после прогона**: `play` часто не добивает уровень до
конца, и база остаётся той же, поэтому список вариантов печатается снова после
`play`, `record`, `rehearse` и `dry-run`. Каждый раз живой макет читается
заново: если клиент успел разобрать другую базу, предложение будет уже по ней
(сравниваются и скелет, и подпись раскладки).

Совпадение только по скелету предложением не считается — вместо него печатается
короткая строка с реальным именем файла:

```
… скелет seed=142614553 знаком (1 запись), но раскладка другая — play не предлагаю
  сыграть всё равно: play! 20261128-135703(1).md, посмотреть другие реплеи этого скелета: replays
```

Имя подставляется из самого свежего файла этого скелета — его можно скопировать
в команду как есть.

## Список записанного (`replays`)

Без аргумента показывает **только текущий скелет** — тот, что загружен на экране:

```
> replays
скелет seed=142614553: 3 записи (в коллекции ещё 1)

seed 142614553: 2 раскладки   <- текущий скелет
  раскладка 1d539025   <- на экране сейчас
    1) 20261128-134121(1).md — 2 прыжка, БЛОКА STATE НЕТ!!!
  раскладка dfc00cec
    1) 20261128-135703(1).md — 3 прыжка
    2) 20261128-141951(2).md — 1 шаг по времени
```

Если под текущий скелет записей нет, печатается только это — чужие записи не
подмешиваются:

```
> replays
ПОД ВАШ СКЕЛЕТ ЕЩЁ НЕТ ЗАПИСЕЙ! (seed=1032192)
  в коллекции 3 записи в 2 базах других скелетов — показать всё: replays all
```

`replays all` — вся коллекция по скелетам; если уровень не загружен, всё
показывается и без аргумента, с пометкой об этом. Помечаются текущий скелет и
текущая раскладка, файлы без блока `state` — как в предложении вариантов. В
строке варианта видно, чем задан план: `5 прыжков` или `3 шага по времени`.

Файлы, которые не читаются, печатаются отдельным списком с причиной — иначе
записанный прогон молча пропадал бы из выдачи:

```
не читаются (2): удалите или запишите заново
  20261128-143936(1).md — в файле нет прыжков (только якорь) — играть нечего
```

## План в миллисекундах

Если в `frames` шаги заданы временем, `play` работает по стенным часам:

- момент старта — якорь (`first_hero_update`): агент запоминает монотонное время
  в момент взвода, дальше отчёт идёт от него;
- шаг `+400ms` означает тап через 400 мс после старта, без пересчёта в кадры и без
  зависимости от фактического FPS;
- точность — порядка интервала опроса (`orchestrator.poll_interval_ms`, по
  умолчанию 3 мс) плюс задержка тапа; фактическое отклонение печатается в
  `INFO orch: ms idx=… err=+…ms` и в отчёте строкой `ms-план: отклонение …`;
- проверка «прыжок случился» остаётся: после тапа смотрится журнал `jumpFn`, при
  промахе — один повтор (`retry_on_miss`);
- `wall_timeout_s` действует как общий предохранитель.

## Воспроизведение (`play`)

1. Файл: `play <файл>` (путь, имя файла внутри `replays/` или `last`), иначе
   автоматически — точное совпадение подписи, затем **тот же скелет**, затем самый
   свежий; причина выбора печатается.
2. Перед тапами подпись сверяется ещё раз. Не совпала — играть нельзя: тапы
   полетели бы по чужой расстановке. Принудительно — `play! <файл>` (или
   `force <файл>`): сверка пропускается, в консоли печатается, какие подписи
   разошлись. Это осознанный выбор оператора, а не тихий обход проверки.
3. Дальше работает прежний оркестратор: живой счётчик кадров, тап в момент
   `frames_to_go * 1000 / fps <= lead`. Состояние из файла подаётся в агент
   только для сверки (`orchestrator.verify_body_frames`).

## Известные ограничения

- «Один в один» — это эталон состояния, а не детерминированная симуляция:
  игра считает физику сама, TAS только тапает.
- `f5` не различает базы с одинаковым скелетом: реплей ищется по подписи.
- Чтение `Dungeon` живёт в двух местах (`base/hook.js` — раскладка для записи и
  reset, `stones/mod.rs::layout_fp` — диагностика `stones raw`). Оба обязаны
  считать FNV-1a 32 одинаково: значение закреплено тестами
  (`stones::tests::layout_fingerprint_*`) и сверено с JS-реализацией.

## Где это в коде

| файл | что делает |
|---|---|
| `TAS/replay.rs` | формат: разбор и запись md, план (кадры и мс), эталон состояния |
| `TAS/library.rs` | каталог `replays/`: подписи, варианты, поиск под текущую базу, список для консоли |
| `TAS/orchestrator.rs` | исполнение: покадровый путь и путь по стенным часам |
| `TAS/capture.rs` | скриншот базы через adb |
| `TAS/main.rs` | меню, диспетчер команд, слежение за базой, запись/воспроизведение |
| `base/hook.js` | какая база загружена, seed, подпись раскладки, ловушки |
| `stones/mod.rs` | диагностика `stones raw` (не участвует в воспроизведении) |

## Проверки

```bash
cargo test --release
node --check base/hook.js stones/rival_hook.js memory/offsets.js
```

Юнит-тесты формата: roundtrip md ↔ память, файл только с `frames`, оба блока и
их совпадение, расхождение блоков, чужая `schema`, чужой fenced-блок,
незакрытый fence, короткая строка `state`, опечатка в `frames`, сжатие в
`loop`, BOM и CRLF.
