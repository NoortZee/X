## Без выпуска — реплеи: запись, идентичность базы и воспроизведение

Формат прогонов переехал из `logs/replay.json` в `replays/<seed>/<время>(N).md` +
кадр в `replays/images/`. Причина не в эстетике: прежний файл держал два источника
истины (скрипт кадров в `"""` и JSON-тело), при расхождении молча выбирал шапку и
отключал сверку, а поиск JSON начинался с первого `{` — так числа `timeline_ns`
однажды стали прыжками.

### Формат

- `TAS/replay.rs` переписан: Markdown-контейнер, `schema: 1`, разбор только внутри
  fenced-блоков (`yaml`/`frames`/`state`), проза и чужие блоки игнорируются,
  незакрытый fence — ошибка. Удалены `extract_json_body`, `timeline_ns`,
  `ReplayEvent.extra`, `mode:`-шапка.
- `state` — источник истины для прыжков и эталона, `frames` остаётся резервом для
  правки руками. Если есть оба и прыжки расходятся, файл считается противоречивым
  и не загружается вместо «молча выберем шапку».
- Первая строка `state` — якорь (он же в шапке); при сравнении с `frames` она не
  учитывается, потому что дельты считаются от якоря.
- Шаги плана бывают двух шкал: кадры (`+26`) и миллисекунды (`+400ms`). Смешивать
  их в одном блоке нельзя. Миллисекундный план исполняется по стенным часам от
  старта уровня и в кадры **не** пересчитывается: агент запоминает монотонное
  время при взводе, `playState` отдаёт `elapsed_ms`, отклонение печатается после
  каждого шага. Покадровый эталон к такому плану не применяется.
- Файл без прыжков (только якорь) не пишется вовсе: инвариант «что записали — то и
  читается обратно» проверяется на сохранении.

### Идентичность базы

- Какая база на экране, определяется хуком `GameScene2::loadDungeon` этой сборки
  (вход `0x1089780`, найден по ссылке на строку `GameScene2::loadDungeon with
  physics %1`; дельта до `setDungeonAndMode` (`0x1089540`) равна `0x240` — как в
  анализе, пролог `setDungeonAndMode` раскладывает `(self, Dungeon*, mode, params)`
  по `rdi/rsi/edx/rcx`). Пролог сверяется перед установкой хука.
- Снимок раскладки копируется в момент загрузки: клиент освобождает объект
  `Dungeon` после обработки ответа, и чтение указателя позже даёт
  `vtable_mismatch`.
- Уход с уровня — отправка результата забега (`SingleplayerAttackResult` /
  `MultiplayerAttackResult`): база перестаёт считаться текущей. Это и был баг, из-за
  которого запись на **своей** базе попадала в папку предыдущей: свой данж сервер
  присылает один раз при старте игры, и «последний разбор» — не текущая база.
- `Dungeon.f5` — скелет (сколько ловушек и какая арена), но **не** уникальный id:
  12 ответов сервера с одним `f5` имели разное золото, уровни и наборы типов.
  Конкретную расстановку различает подпись раскладки (FNV-1a 32 по
  `slot/type/x/y`), которую считает `base/hook.js`.
- Исправлен off-by-one в таблице `repeated` у `base/hook.js`: элемент i лежит по
  `rep+8+i*8`, прежнее чтение с `rep+0` отдавало мусор первым и теряло последнюю
  ловушку (проверено на живом ответе: `rep0[i+1] == rep8[i]` на всех 10 парах).

### Запись

- Папка — `replays/<seed>/`, файл — `<YYYYmmdd-HHMMSS>(N).md`, кадр —
  `replays/images/<…>(N).png`, ссылка в шапке `../images/…`.
- Номер варианта считается по паре (скелет, раскладка): `max(существующие)+1`,
  файлы без номера занимают слоты снизу.
- Скриншот базы снимается в момент `first_hero_update` через
  `adb exec-out screencap -p` (отдельный поток, таймаут, проверка `IEND`). Waydroid
  пишет в stdout предупреждение графического стека перед PNG — картинка вырезается
  по сигнатуре, а не предполагается с нулевого байта.
- В блок `state` попадают только кадры прыжков и якорь.
- Хуки модуля `base` ставятся на старте сессии: они read-only, пока не взведён
  reset, а раскладка нужна и записи, и сверке перед `play`.
- Ретенция — последние `replays.keep_per_base` прогонов на базу, пара md+png
  удаляется вместе. `clear` чистит только консоль.

### Воспроизведение

- Файл: `play <файл>` (путь, имя внутри `replays/`, `last`), иначе автоматически —
  точная подпись, затем **тот же скелет**, затем самый свежий, с причиной выбора.
- Перед тапами подпись сверяется с живой; не совпала — отказ. Принудительно —
  `play! <файл>` или `force <файл>`: сверка пропускается, расхождение печатается.
- Слежение за базой: раз в 300 мс читается сохранённый при загрузке макет, при
  смене счётчика загрузок печатается список вариантов (`y`, `y <номер>`);
  обновляется и после `play`/`record`/`dry-run`, потому что база остаётся той же.
  Совпадение только по скелету предложением не считается — печатается подсказка с
  реальным именем файла.
- `replays` — список записанного: без аргумента только текущий скелет
  (`replays all` — вся коллекция); помечаются текущая раскладка, тип плана
  (`5 прыжков` / `3 шага по времени`), отсутствие `state` и нечитаемые файлы с
  причиной.
- Голый номер варианта (`1`, `2`, …) или `png <номер>` открывает кадр системным
  просмотрщиком (`replays.viewer`, по умолчанию `xdg-open`).

- Кадр базы снимается один раз на пару (скелет, раскладка): второй вариант того же
  уровня переиспользует существующий PNG (`existing_screenshot`), в консоли —
  `кадр базы уже есть — переиспользую: …`.
- Ретенция больше не уносит общий кадр: перед удалением проверяется, ссылается ли
  на него кто-то из оставшихся прогонов (`prune_base_dir`). Раньше удаление старого
  варианта ломало картинку нового.
- Тесты: `screenshot_is_reused_for_the_same_skeleton_and_layout`,
  `pruning_keeps_a_screenshot_shared_with_a_newer_variant`.


- Переиспользование кадра перестало зависеть от порядка: TAS печатает раскладку
  перед записью (`(база: seed=… раскладка=…, ловушек …)`), повторяет чтение при
  пустом ответе, а если раскладка прояснилась только к концу — берёт существующий
  кадр и удаляет дубль (`adopt_existing_shot`).
- Тест `late_layout_adopts_the_existing_screenshot`.
- Разбор случая: два прогона легли в `replays/seed0/` с двумя PNG не из-за ошибки
  переиспользования, а потому что раскладка не была прочитана вовсе (уровень собран
  до запуска TAS) — без скелета и подписи совпадение искать не по чему. Теперь это
  видно в консоли до начала записи.


### Мелкое

- `logging.log_dir` заменён секцией `replays`; старый ключ читается с
  предупреждением. `start/start.sh` экспортирует `KOT_TAS_ADB_DEVICE`, а контракт
  `tests/test_tap_scaling.py` («launcher экспортирует ровно те `KOT_TAS_*`, которые
  читает Rust») расширен на это имя.
- Тест `phantom::tests::detects_dead_server_on_eof_ping` был флейки (один слушатель
  на все попытки): теперь каждая попытка со своим слушателем.
- Библиотека реплеев — каталог, подписи, варианты, поиск под текущую базу, список —
  вынесена в `TAS/library.rs` (831 строка вместе с тестами); `TAS/main.rs` остался
  меню, диспетчером команд и записью/воспроизведением (2261 → 1459 строк).
- Убран `#![allow(dead_code)]`: сборка больше не прячет мёртвый код. Заодно
  удалены неиспользуемые `prompt_or_detach`, `TasAgent::detect_get_frame_ns_timeline`
  (таймлайн в формате не нужен) и `BaseError::BadRpc`; мёртвые `with_steps`, `text`,
  `first_parse_ptr`. Повторяющиеся фрагменты сведены к одному месту:
  `ReplayVariant::from_peek`/`line`, `DungeonWatch::live`, `load_for_play`,
  `replay::collect_blocks`.
- Документация: `docs/REPLAY.md` (формат, правила, команды, «где это в коде»),
  `docs/START.md`, `docs/MEMORY.md`; четырнадцать отдельных подразделов этого
  раздела про реплеи свёрнуты в один связный текст без повторов.

## Без выпуска — сбор серверных данных для формата replays

Перед сменой формата реплеев нужно знать, что сервер вообще присылает: id
подземелья, раскладку ловушек и seed. Пока эти поля не подтверждены живьём,
опираться на них нельзя, поэтому добавлен отдельный read-only сбор данных.

- `stones raw` — полный дамп ответа `Response_RivalDungeon` в
  `diag/rivals-<unix>.jsonl`: скаляры, окно сырых dword, строковые поля,
  вложенные сообщения, repeated-поля и `Dungeon` (заголовок + ловушки). Команды
  внутри режима: `skip` (следующий соперник), `now`, `clear`, `stones stop`.
  Дамп включается только явно, по умолчанию агент ничего не читает сверх
  обычного снимка.
- Там же пишутся исходящие сообщения `start_attack`, `confirm_dungeon`,
  `attempt_started`, `matchmaking`, `league_rival` и `change_dungeon_object`:
  так видно, в каком запросе появляется id подземелья (в живом
  `ConfirmDungeon` он приходил как `f1 = 17`).
- `memory/offsets.js`: новые только наблюдательные разделы —
  `stones.rival_probe` и `protocol.dungeon.header`/`probe` (`seed` = `+0x38`,
  тот же `142614553`, что в сохранённом пакете). Ничего не пишется в игру:
  все чтения обёрнуты в try/catch, запись в память отсутствует.
- `Dungeon.obstacles` дампится в двух интерпретациях (`rep+0` как в
  `base/hook.js` и `rep+8` как в `stones`): расхождение в чтении repeated-поля
  закрывается фактом с живого ответа, а не правкой вслепую.
- Формат реплеев в этой работе не менялся (он переделан выше по файлу).

## Без выпуска — mystic: автозбор колб в Mystic Realm

Ивентовый режим Mystic Realm даёт 60 секунд на сбор колб трёх редкостей. По
аналогии с `catacombs` собран модуль, который сам телепортирует колбы к герою.

- Найдено по RTTI (новый инструмент `analysis/rtti_find.py`): классы
  `MysticRealmPlayState` (typeinfo `0x2015770`), `MysticRealmReagent`
  (vtable `0x2048f18`), `MysticRealmTrap`, `MysticRealmReagentPreview`.
  Пер-кадровый апдейт режима — слот 17 vtable (`0x1468cc0`): тот же слот, что у
  `EndlessMazePlayState` (`0x14d7350`, он же сигнатура в `catacombs`), поэтому
  состояние режима приходит первым аргументом хука.
- Колбы используют тело `EndlessMazeCandyBody`, поэтому телепорт — та же
  механика, что у Candy: запись stored x/y в теле (`+0x38/+0x3c`) и
  `destroy` (`0x1615cb0`), который пересоздаёт тело в новой точке; после —
  сверка позиции из физики.
- Новый модуль `mystic/` (`agent.js` + `mod.rs` + `README.md`), команды меню
  `mystic` (загрузить модуль + памятка) / `mystic on` / `mystic status` /
  `mystic timer <N>` / `mystic off`, Ctrl+C в меню выгружает модуль, как у
  `catacombs`; секция `mystic` в
  `memory/offsets.js`. Фильтр колб — по `vptr` (сравнение указателя вместо
  чтения RTTI-имени у 270 объектов), `NativeFunction` для destroy создаётся
  один раз — без этого были заметные просадки в забеге.

Найденная на живом прогоне поломка: проверка пролога в `byRva` ждала
оригинальные байты, а если по адресу уже стоял трамплин чужого хука (`E9 …`,
прошлый сеанс или второй TUI), установка падала молча — `hooked: false`, и
таймер со сбором просто ничего не делали. Теперь трамплин принимается как
«уже перехвачено», `start`/`setTimer` повторяют установку, а в статусе при
отсутствии хука печатается `ХУК НЕ СТОИТ` (есть юнит-тест на эту сводку).

Таймер: оставшееся время забега — `MysticRealmPlayState+0x1e0` (float), update
вычитает из него dt и по нулю завершает забег. Команда `mystic timer <N>`
подрезает поле вниз до N (вверх не пишет, чтобы таймер не «оживал») и включает
автозбор. Значение — аргумент команды: проверено живьём на 5 секундах, дальше
на 3 (`mystic timer 3`) — забег укладывается в три секунды, колбы при этом
собираются пачкой на первом тике.

Попытка увеличить награду спавном колб закрыта: путь спавна — `0x16079e0`
(ctor `0x15bc350` с адресом возврата `0x16079fb`, `ctors=66` за забег), но
клоны, созданные этим же вызовом с пойманными аргументами `(source, scene)`,
игра в награду не засчитывает. Режим `mystic spawn` убран из кода (мёртвый
путь не оставляем), адреса остались в `memory/offsets.js` как справка; дальше
смотреть надо счётчик прогресса, а не объекты уровня.

Замеры в живых забегах (2.84.2): 27 колб (первый вариант, лаги) → 61 после
кэша `NativeFunction` и фильтра по vptr (лагов нет) → 66 при пакете 8 колб за
тик и интервале 60 мс (прироста нет, тик до 83 мс). Вывод: узкое место — не
цикл телепорта, а появление колб на уровне (~1/с); безопасный профиль — пакет 3,
интервал 100 мс, точка сбора в 12 px перед героем. Дальше скорость упирается в
спавн (фабрика по адресу вызова `0x16079f6`) или в счётчик прогресса — это
отдельная задача, в модуле не сделано.

Тесты: `cargo test` — 23/23 (добавлены тесты сводки и справки `mystic`),
`node --check` для `mystic/agent.js` и `memory/offsets.js`.

## Без выпуска — base: команда `reset` (все объекты макета в одну точку)

В `base` был только сдвиг дельты редактора (`ChangeDungeonObject`). Нужен был
режим, который локально (только у меня) собирает все объекты базы в одну
видимую точку — чтобы разбирать базу после сдвигов, а не искать объекты по
арене глазами.

- В `memory/offsets.js` добавлена секция `protocol.dungeon`: RVA парсера
  `Dungeon::MergePartialFromCodedStream` (`0x105c7c0`) с прологом для проверки,
  vtable `Dungeon` (`0x1f70598`), смещения `Dungeon_Obstacle` (`count` +0x20,
  `rep` +0x28, `x`/`y` +0x18/+0x1c, слот +0x20, тип +0x48) и точка по умолчанию
  (448, 224). AOB-сигнатуры у protobuf-парсеров не уникальны (общий пролог), поэтому
  адрес берётся по RVA, а пролог сверяется перед хуком.
- `base/hook.js`: хук на парсер `Dungeon`; команда `reset` правит `x`/`y` у всех
  объектов `f1` на заданную точку. Режим держится до `base reset off` и
  срабатывает на каждом разборе раскладки. Пишутся только записи, похожие на
  `Dungeon_Obstacle` (тип 1..255, слот 0..64, указатель читается); остальные
  считаются в `skipped`. Пролог парсера сверяется с повторами (сразу после
  старта игры страницы кода готовы не сразу — без повторов хук молча не вставал,
  это поймал живой прогон). Добавлена диагностика: счётчик разборов, флаг
  `reset.hooked` и `trace` в `status`.
- `base/mod.rs`: `base reset [<x> <y> | off]`, строка лога
  `[base] reset: N объектов -> (x, y) [layout] всего M`, `BaseSnapshot` для
  восстановления режима после переподключения, обновлён `HELP`.
- `TAS/main.rs`: сессия с игрой стала сменяемой. Перезапуск игры больше не
  убивает `kot-tas`: главный цикл ждёт появления процесса, подключается заново и
  пересоздаёт модули, а последнее состояние `base` (смещение, on/off, reset с
  точкой) восстанавливается вместе с хуками —
  `INFO main: base восстановлен: BaseSnapshot { … }`. Ожидание команды в меню
  теперь проверяет `session.is_detached()` каждые 50 мс, иначе смерть игры была
  видна только на следующей команде и приложение висело на мёртвом RPC.
- `analysis/reconnect_check.py` — живая проверка переподключения на pty:
  старт TUI, `base reset`, `am force-stop`, запуск игры заново, `base status`.
- `analysis/base_reset_probe.py` — живая проверка агента через Phantom-порт
  (`adb forward tcp:27183`) со сборкой скрипта как в `memory::prepend_layout`;
  скриншот живой проверки — `analysis/base_reset_live.png`.

Живая проверка (2.84.2 x86_64, Waydroid, клиент перезапущен и режим включён до
входа в базу): разобрано 12 макетов `Dungeon` (по 10–11 объектов), переписано
120 объектов, координаты до правки совпадают с `ConfirmDungeon.f4/f6`
(типы 1/2/11/12/21/39/42/47, координаты 32..896). База после перезахода
съехала к заданной точке, но клиент разложил объекты по соседним клеткам —
выходит плотная группа, а не одна стопка.

Проверка переподключения (`analysis/reconnect_check.py`): `base reset` →
`am force-stop com.zeptolab.thieves.google` → `ERROR main: frida session lost` →
`INFO main: соединение с игрой потеряно — жду перезапуск игры` → запуск игры →
`INFO main: attached to King of Thieves (pid=60031)` → хуки поставлены заново →
`INFO main: base восстановлен: BaseSnapshot { offset: (-64, 0), enabled: false,
reset: Some((448, 224)) }` → `base status`: `"reset":{"armed":true,"hooked":true}`.
Выход по `q` завершил процесс с кодом 0.

**Не сделано:** живой список объектов уровня. Клиент рисует сцену из уже
созданных объектов, поэтому правка сообщения не двигает то, что на экране,
и требует нового разбора раскладки. Настоящая стопка в одной точке требует
записи `x`/`y` в объекты уровня (`scene+0x258/0x260/0x288/0x290`), для чего
нужно найти источник указателя на сцену в этой сборке — отдельная задача.

Тесты: `cargo test` — 20/20, в том числе `base::` (помощь упоминает `base reset`,

## Совместимость

Профиль `memory/offsets.js` снят с King of Thieves **2.84.1, x86_64**, библиотека `libthieves.so`, и проверен без изменений на **2.84.2**.
Это описание профиля, а не жёсткая привязка к одной сборке: `game_version` нигде не сверяется с версией установленной игры.
Функции (FRAME_FUNC, JUMP, разморозка, парсер соперника) резолвятся в первую очередь по AOB-сигнатурам; резервные RVA используются только при нуле совпадений и устаревают первыми при сдвиге кода.
Поля читаются по относительным смещениям структур (`tas.hero`, `tas.body`, `stones.rival_fields`), а не по абсолютным адресам, поэтому обновление, не меняющее раскладку, карту не ломает.
Для HeroBody указан FRAME_FUNC `0x1612A20`; старая сигнатура также находила другое тело по `0x161B7C0`.
При смене сборки, меняющей код функций или раскладку структур, правится только `memory/offsets.js` — пересборка Rust не требуется (см. `docs/MEMORY.md`).
