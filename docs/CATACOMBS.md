# Catacombs: новая диагностика объектов

Модуль опирается на LIVE-кандидаты EndlessMazePlayState/EndlessMazeCandy, а не старые ExpCrumb/DeathSkull/CollectSkulls. По умолчанию только чтение. Явная экспериментальная команда move-white один раз меняет два поля позиции одного существующего common; коллизии, награды и количество предметов не меняет, функции игры не вызывает.

## Обновление и запуск

Из корня проекта:

```sh
git pull --ff-only
cargo build --release
./start/start.sh
```

Первое обновление требует пересборки Rust. Далее правка только карты/агента требует stop/start модуля, не пересборки.

Команды вводить по одной с Enter:

```text
catacombs start
catacombs status
catacombs mark entered
catacombs mark picked-golden
catacombs mark trap-hit
catacombs mark finish
catacombs dump
catacombs stop
```

Метки ставьте после соответствующего действия, если удобно переключаться в терминал. Они ручные: время отметки не равно точному времени игрового контакта. Если переключаться неудобно — сделайте dump сразу после финиша и опишите действия.

Каждый dump создаёт новый файл `logs/catacombs/report-<timestamp>.json`, путь печатается в терминале. Каталог не удаляется обычной стартовой очисткой файлов logs. Файлы сами не ротируются: старые отчёты нужно удалять вручную. Dump делайте **до stop** — выгрузка уничтожает историю агента. Повторный start при загруженном агенте не сбрасывает историю; для нового эксперимента stop/start.

## Состав отчёта

- metadata: процесс/архитектура/база/размер библиотеки и вся кандидатная карта смещений. Версия профиля не является измеренной версией игры; ELF-хеш не вычисляется.
- resolution: адрес и RVA единственного найденного update Endless. Используется сигнатура проверенного начала 0x14D7350, не ошибочная сигнатура ReplayState из старого отчёта. Ноль/несколько совпадений запрещают установку хука, fallback по RVA отсутствует.
- latest: последний ограниченный граф state → world/MultiHero → Hero → HeroBody → physics; RTTI полиморфных объектов, позиции Hero, физические поля по общей карте TAS. Координатные системы Hero/Candy и физики могут отличаться: значения не смешиваются и не используются для телепорта.
- object_graph: ZArray-кандидат state+0x68, data/+0x10, slots/+0x18; слоты, адреса, RTTI всех просмотренных объектов, позиция-кандидат +0x34/+0x38, распределение классов. Поддержка разреженных null-слотов. У каждого поля может быть error вместо значения.
- candies: только объекты с точным RTTI `16EndlessMazeCandy`; позиция, raw rarity/+0x1F0, flags/+0x1A8/+0x1A9, связанные body/+0x198 и image/+0x1A0 с RTTI, четыре первых виртуальных адреса без их вызова. Rarity не переводится автоматически в цвет; сопоставление 1..4 из LIVE-отчёта остаётся гипотезой.
- history: последние 120 снимков с состоянием, героем, распределениями и Candy. Последний полный граф отдельно в latest.
- events: последние 1000 наблюдений/изменений Candy, ручные метки, ошибки и смена объекта состояния. `candy_not_in_array` — отсутствие в полном успешном обходе, **не доказанный подбор**: возможны выгрузка участка/переиспользование адреса. При ошибках RTTI/слотов или усечении обхода исчезновение не выводится. Промежуточные события между снимками могут быть пропущены.

## Ограничения и безопасность

Снимки раз в 500 мс, максимум 1024 слота на обход. Число слотов вне 0..16384 отклоняется; выше 1024 — явное усечение, без выводов об исчезновении. Имена RTTI читаются до NUL, не более 128 байт. Нет рекурсивного обхода произвольных указателей и полного дампа процесса. Указатели разыменовываются только в текущем update callback, не при RPC dump; ошибки чтений фиксируются. Раскладка массива всё ещё кандидатная и требует проверки на устройстве.

История/события ограничены: долгий забег вытесняет начало, поэтому полезны несколько dump. Снимки могут создавать нагрузку на игру; если появляются задержки, остановите модуль. Не запускайте record/play во время эксперимента. Тайм-ауты RPC: 30 сек start, 5 сек status/dump/mark; Ctrl+C отменяет ожидание, но синхронные load/unload Frida не покрыты этим тайм-аутом.

Первый эксперимент: включить до входа, войти в Catacombs, подобрать несколько черепов разных редкостей, отметить/описать попадания, завершить уровень и сохранить отчёт. Желателен dump сразу после входа и после подбора. Одного запуска недостаточно для гарантированной идентификации контакта/награды; доказательства нужно сопоставить с HUD. Серверные начисления не исследуются и не подделываются.

## Поиск штатного перемещения Candy

Новые `position_method_candidates` содержат указатели из vptr Candy по смещениям 0x238 (кандидат setter), 0x268 (кандидат getter) и 0x10 (slot2). Это гипотезы по прежнему анализу базового объекта, а не подтверждённые ABI или имена. `body_method_candidates` отдельно сохраняет первые четыре метода связанного Body.

`method_code` содержит кэш байтов/дизассемблера этих целей: только readable/executable память игровой библиотеки, до 24 уникальных целей, до 384 байт и 128 инструкций на цель. Всё читается в текущем callback update при наличии объекта. Повторные dump используют кэш, старые объектные указатели не разыменовываются. Если цель недоступна, сохраняется error; для повторного чтения нужен stop/start. Полнота функции и граница кода не гарантируются, окно может включать соседний код. Прямые call/jmp могут вести за пределы окна. Никакие виртуальные методы не вызываются, хуки на эти цели не ставятся.

После обновления достаточно stop/start модуля (Rust не менялся). Включите до входа, войдите в Catacombs, соберите один common штатно, затем выполните dump до stop. Полный забег не требуется: нужны наблюдаемые Candy/Body и код их методов. Метка `catacombs mark picked-common` поможет сопоставлению, но это время ручной команды, не точного контакта. Пришлите новый JSON из logs/catacombs.

По снятому коду setter подтвердился как простая запись двух float. Ниже добавлен явный одноразовый эксперимент; синхронизация Body и факт зачёта остаются непроверенными.

## Эксперимент: перенести один common

**Требуется пересборка `cargo build --release`**, поскольку добавлена Rust-команда. Обновите проект и перезапустите TAS. Включите модуль, войдите в активный Catacombs, затем отдельно введите:

```text
catacombs move-white
catacombs status
catacombs dump
```

Команда ставит запрос, а не пишет память из RPC. На выходе ближайшего Endless update выполняется **одна попытка**: заново проверяются this/RTTI, phase=1, paused=0, цепочка Hero/HeroBody, направление ±1, массив не более 1024 слотов. Выбирается ближайший существующий Candy типа 1 из текущего массива. Его координаты записываются в `(Hero.x + direction*24, Hero.y)` — в координатах объектов, не Box2D.

Перед записью проверяются права полей и точные 8 байт текущего виртуального setter из присланного дампа (`mov rax,rdi; movlps [rdi+0x34],xmm0; ret`). Запись двух float воспроизводит этот setter без непроверенного NativeFunction ABI. При ошибке записи предпринимается немедленный rollback; его исход записывается. После удачной записи автоматического восстановления/повторных попыток нет. Физические тела/флаги/редкость/счётчики/запросы не меняются.

Запрос привязан к адресу состояния и действует до 5 секунд, stop отменяет его. До выполнения проверяются актуальные указатели, не snapshot-указатели. Это уменьшает риск, но не гарантирует отсутствие гонки или переиспользования адреса. Выход из Endless update — не доказательство состояния всех потоков физики; код не вызывает физические функции, однако эксперимент всё равно может дать визуальный перенос без контакта/зачёта.

`queued` не означает выполнено. В status и dump смотрите `last_move` (`before`, `target`, `readback`, `success`/`error`), `moves_executed` и `move_white_result`. `success` означает успешную запись, **не подбор** (`collection_confirmed` всегда false). Если нет callbacks, запрос не выполнится и останется pending до следующего update/stop; при следующем update истёкший запрос отклоняется.

Для первой проверки запомните HUD, вызовите команду **один раз**, дайте герою пройти несколько шагов и сравните HUD: ожидаемый результат эксперимента — +1 common, но он пока не гарантирован. Затем dump и пришлите файл с описанием видимого результата. Если только картинка сместилась, предмет вернулся назад или счётчик не изменился — не повторяйте массово: будем исследовать синхронизацию Body. Притяжения всех черепов, noclip и спавна новых предметов здесь нет.

## После визуального переноса без зачёта

В отчёте report-1795205373689069174 обе команды выбрали один Candy; после первой записи его object-позиция вернулась с (554.56,804.56) на (704,722), объект остался в массиве до последнего снимка. Обычные подборы пользователя не считаются результатом команды.

Следующая версия добавляет **только диагностику физического пути**, не обещает исправление зачёта. `physics_candidate` проверяет CandyBody RTTI, читает кандидат +0x20 по аналогии с HeroBody, поля предполагаемого b2Body и сравнение object.xy с physics.xy*100. Это гипотеза структуры: даже совпадение координат не доказывает ABI или корректность записи. Никаких записей в тело и вызовов неизвестных функций нет. Ошибки читаются как error.

`body_handler_calls` сохраняет код до 8 прямых call из окна slot3 Body, только один уровень, в общем ограничении 24 целей. Окно может включать соседние функции: наличие call не доказывает принадлежность обработчику. Косвенные вызовы не разыменовываются и не вызываются.

Для диагностики достаточно stop/start без пересборки Rust. Включите до входа, постойте/пройдите в уровне, подберите один черепок штатно и выполните dump до stop. Повторять move-white не требуется: пока команда осталась прежним координатным экспериментом без подтверждённого зачёта. Новый JSON нужен для проверки CandyBody/физики и выбора штатного SetTransform/контактного пути, а не для подмены счётчика наград.

## Проверка предложенных lifecycle RVA

В `lifecycle_candidates` добавлены пользовательские **неподтверждённые** RVA относительно текущей базы libthieves.so:
- `0x1618980`: кандидат обёртки позиции;
- `0x1615CB0`: кандидат удаления физического тела;
- `0x1617DE0`: кандидат создания/инициализации.

На первом sample после start читается код всех трёх корней, затем до 6 прямых call суммарно на один уровень. Все записи входят в прежний общий бюджет 24 целей × до 384 байт/128 инструкций. Приоритет трёх корней выше факультативных вызовов. Никакого вызова этих функций/новых хуков, destroy/create или setImmediate нет. Окна не доказывают границы функций и могут включать соседей; роли и ABI ещё не подтверждены. RVA вне модуля отклоняется, неисполняемая/недоступная память отражается как error. Отчёт использует кэш, повторное чтение — stop/start.

У Candy physics в `extra_candidates` отдельно читаются float `+0x28/+0x2C` и указатель `+0x58`. Это кандидаты sweep/world, а не замена уже сопоставленных transform `+0x0C/+0x10`; указатель world не разыменовывается. Ошибка отдельного дополнительного поля не скрывает основной transform.

Обновите JS/карту, выполните `catacombs stop`, `catacombs start`, войдите в уровень и затем `catacombs dump` до stop. Rust пересобирать не надо. move-white не требуется и по-прежнему не гарантирует подбор. Для анализа пришлите новый JSON; только после проверки кода можно выбирать дальнейший эксперимент с collision.

### Уточнение после отчёта report-1795206544892669635

Код 0x1615CB0 не является только destroy: после удаления и обнуления physics указателя он передаёт управление виртуальному методу Body+0x68 с сохранённой позицией/world. Вызов destroy и затем отдельный create не разрешён этим наблюдением. Принадлежность обёртки 0x1618980 классу CandyBody не доказана; конфликт использования +0x70 требует проверки, функции не вызываются.

В следующем дампе `body_method_candidates.recreate_candidate` читает **реальную цель vptr+0x68 текущего CandyBody** (без прибавления заголовка RTTI). Create-кандидат 0x1617DE0 получает окно до 1536 байт/512 инструкций вместо прежних 384/128, чтобы увидеть продолжение инициализации. Остальные окна остаются 384/128; общий кэш увеличен до 40 целей (верхний предел сырых байтов 60 KiB при максимальном размере каждого окна, фактический меньше). Ограничения модуля/доступности сохраняются.

Прямые lifecycle callees теперь имеют независимый бюджет **4 уникальные цели на каждый корень**, а не общий бюджет, который раньше забирал первый кандидат. Линейный просмотр заканчивается на первом ret/int3, чтобы не включать очевидный соседний код. Это не CFG-анализ: блоки после раннего ret и tail-jmp не обходятся, полнота функции не заявляется. Код вызванных функций не обходится рекурсивно.

Порядок проверки прежний: обновление, stop/start, активный уровень, dump до stop. move-white не нужен. Это всё ещё read-only диагностика lifecycle, не исправление зачёта и не вызов пересоздания. Пересборка Rust не требуется.

## Явный эксперимент `teleport-white`: пересоздание одного физического тела

Требуется **`cargo build --release`** после обновления: добавлена новая Rust-команда. Старый `move-white` остаётся визуальным экспериментом; для физического переноса используйте отдельно `catacombs teleport-white`.

Запрос исполняется один раз в onLeave текущего Endless update на том же потоке, без setImmediate. После свежих проверок состояния/Hero/направления/массива/rarity=1 выбирается один ближайший common. Дополнительно проверяются:
- RTTI CandyBody, статический тип physics=0, совпадение physics.xy*100 с object.xy;
- обратная ссылка physics+0xB8 на выбранный CandyBody и ненулевой world из physics+0x58;
- точные runtime-байты начала rebuild (64 байта), create (40) и удаления b2Body (40) из отчёта report-1795206913385119108, readable/executable код в пределах модуля;
- фактический vptr+0x68 равен module+0x1617DE0;
- сохранённые float Body+0x38/+0x3C совпадают с object.xy;
- бит 2 world+0x19298 сброшен непосредственно перед записью/вызовом.

Затем записывается сохранённая Body-позиция `(Hero.x±24, Hero.y)` и вызывается **только** module+0x1615CB0 с ABI void(CandyBody*). Его код сам удаляет тело и вызывает проверенный create-слот с world и Vector; прямой вызов функции с Vector ABI не нужен. Отдельного второго create нет. Физические координаты нового тела считываются и сравниваются с целью (допуск 0.05 в object-единицах). Адрес тела может остаться тем же из-за аллокатора; это не признак отсутствия пересоздания.

**Риск остаётся:** onLeave и lock-check не доказывают отсутствие гонок с другими потоками; пересоздание может влиять на контакты/фикстуры/callback и аварийно завершить игру. Проверены мок-тесты, а не live-вызов. Награды/счётчики не меняются, `collection_confirmed` остаётся false. `success` подтверждает native возврат и физические координаты, не зачёт.

Одна попытка записи на запуск модуля: `teleport_used` блокирует следующий teleport до stop/start. После ошибки native состояние неопределённо: **нет rollback/повтора** и нельзя считать игру восстановленной. При ошибке до native, но во время записи координат, предпринимается только немедленный rollback этих двух полей. `mutation_attempted`/`diagnostic_only` учитывают даже неуспешную попытку записи. Stop отменяет только pending-запрос, не откатывает выполненную попытку. RPC timeout/Ctrl+C не гарантируют отмену уже поставленного запроса.

Для первого теста: перезапустите TAS с новой сборкой; включите `catacombs start`, войдите в активный уровень, запомните HUD и выполните **один раз**:

```text
catacombs teleport-white
catacombs status
```

Дайте герою пройти несколько шагов и выполните `catacombs dump` до stop. Пришлите JSON и отдельно сообщите, изменился ли HUD на +1 common, был ли визуальный перенос/возврат/краш. Обычные подборы не приписывайте команде. При error или отсутствии зачёта не повторяйте через stop/start ради массового сбора — сначала анализируем результат.

## Текущий режим: автоматический перенос всех редкостей + компактный dump

После успешного одиночного live-теста автоматизация включена по умолчанию в `memory/offsets.js`: `auto_teleport.enabled=true`. Сам модуль по-прежнему запускается явно командой `catacombs start` и останавливается `catacombs stop`. Это разрешает **реальные native-пересоздания**, не только чтение.

Включите модуль до входа в Catacombs. От первого наблюдаемого active phase=1 отсчитывается 300 мс (если включили посреди уровня — отсчёт от первого увиденного активного update, не настоящего старта). На выходе update после этого времени переносится максимум один Candy за callback, не чаще 20 мс, с повторным сканированием свежего массива. Обрабатываются rarity 1/2/3/4, включая вновь загруженные объекты уровня. Это начало серии через 300 мс, **не обещание перенести всё за 300 мс**. Последовательность уменьшает пик нагрузки, но её live-устойчивость ещё требует проверки; в том числе золотая редкость ранее отдельно не проверялась.

Сохраняются все проверки `teleportCandy`, включая физический owner, координаты, точные сигнатуры, recreate-slot и unlocked world. При pause переносы не выполняются; отсчёт wall-clock продолжает идти. Locked world откладывает попытку. Любая другая ошибка останавливает автоматику уровня (`auto_run.halted/error`), без повторения потенциально частично выполненного native-вызова. Счётчики `attempted/moved` отражают попытки/успешный физический readback, **не количество зачисленных наград**.

Пара object-address:Body-address помечается до попытки и не переносится повторно в том же уровне. Если аллокатор переиспользует оба адреса для нового предмета, такой предмет будет консервативно пропущен. Смена state или наблюдаемый выход из phase=1 очищают очередь дедупликации; если переход уровня не был виден callback и адрес state сохранился, автоматическое распознавание нового забега не гарантируется. Stop полностью отключает обработку; отменить уже исполняемый native-вызов нельзя. В автоматическом режиме ручные move-white/teleport-white отклоняются, чтобы не смешивать режимы. Старый лимит одной попытки ручного teleport не ограничивает автоматическую серию.

`diagnostics=false` по умолчанию: тяжёлые графы, object history, RTTI-снимки всех слотов и дизассемблер **не собираются**. Schema 3 compact dump содержит status/auto_run, last_move, краткий последний state и до 80 последних событий; полная карта смещений/сигнатур не дублируется. Длинная серия может вытеснить ранние события, но суммарный moved остаётся в auto_run. Для специального исследования можно вернуть diagnostics=true и stop/start — прежний тяжёлый диагностический формат сохранён как опция. Не обрезайте JSON вручную.

При error, краше или отсутствии зачёта не перезапускайте автоматику ради повторного массового вызова — сохраните результат для анализа. ## Исправление ложной остановки на больших координатах

В report-1795211333009023329 auto_run.halted=true после 6 успешных переносов; причина `rebuilt physics position differs from target`. При малых координатах допуск остаётся около 0.05; при Y≈1.6млн около 0.37 object-единиц, не десятки пикселей. Не-finite значения отклоняются. Исправление численной проверки не возвращает пол, не останавливает падение, не гарантирует обработку всех контактов на скорости ×5 и не подменяет статистику. Рабочие speed/mask/алгоритм переноса не изменялись. ## Без падения при noclip

`no_fall.enabled=true` включает подавление вертикального движения при применённом mask_test для текущего state. В текущем update onEnter и onLeave заново проверяется Hero/HeroBody, physics owner-chain/lock через heroMaskContext, dynamic type=2 и доступность полей. В physics ставятся gravityScale (+0xA8 из общей TAS-карты)=0 и VY(+0x44)=0. Горизонтальная скорость, transform/sweep и Hero.xy не меняются. OnEnter предотвращает очередное гравитационное ускорение после первой успешной активации, onLeave убирает появившуюся вертикальную скорость. Это эксперимент на известных TAS-полях, live-результат ещё требует проверки.

Это **не восстановление пола** и не телепорт на прежнюю высоту: герой должен перестать падать на текущей высоте, прыжки/естественное вертикальное движение будут подавлены. Если модуль включён после длительного падения, координату Y назад он не вернёт. Если игра сама напрямую меняет transform вне физической скорости, такой путь этой правкой не блокируется. Рабочие маски/скорость ×5/перенос Candy сохранены.

Оригинальная gravityScale запоминается один раз для текущего тела. При stop/наблюдаемом выходе из active phase восстанавливается только gravityScale с проверкой свежих Hero/physics и отсутствия чужого изменения значения. Старый VY **не восстанавливается**, чтобы не вернуть накопленную скорость падения. Locked/сменившееся/недоступное тело → deferred_or_failed/restore_failed, без записи по устаревшему адресу. При исчезновении callbacks/принудительной выгрузке cleanup не гарантирован; stop перед другими режимами обязателен, при restore_failed перезапустите игру.

Компактный status/dump содержит no_fall.status/original_gravity/gravity/vy/physics/error. Обновите файлы после stop старого модуля, пересборка Rust не нужна. Start перед новым уровнем, проверьте высоту героя несколько секунд и сбор, затем dump. Отключение: no_fall.enabled=false в карте перед новым start, предварительно stop текущего агента.

## Небольшой спуск под стартовую поверхность

По просьбе пользователя `no_fall.underground=true`: при первом включении no_fall запоминается текущий Hero.y и фиксированная цель **Y+64 object-единицы** (примерно одна клетка вниз; в наблюдаемой системе вниз = плюс Y). Координаты Hero/transform/sweep не пишутся: пока цель не достигнута, при gravity=0 задаётся VY=+2 physics-единицы/с, затем VY=0. Цель не пересчитывается от каждого кадра, поэтому бесконечного накопительного падения нет. Прохождение этой глубины занимает примерно 0.32с при стандартном масштабе 100:1, фактический результат зависит от обновления игры.

В no_fall status/dump добавлены start_y/target_y/current_y и descent=descending/complete/timed_out. Ожидание ограничено 2000мс wall-clock: если игра сама сбрасывает скорость или герой не достиг цели, спуск останавливается без повторов. Pause не выполняет запись, но учитывается в wall-clock сроке, поэтому длительная пауза может привести к timeout после продолжения. При stop/выходе фазы VY явно обнуляется перед восстановлением gravityScale, чтобы не оставить принудительный спуск включённым.

Это ограниченный начальный спуск, а не гарантированное удержание под любой геометрией уровня. После достижения цели действует прежний no_fall. Высота не корректируется вслед за неровным полом, прямые игровые телепорты/смена уровня могут переместить героя. Маски/×5/автоперенос Candy сохраняются. Нахождение ниже пола не доказывает иммунитет к ловушкам и может повлиять на финиш/сенсоры.

Обновите файлы после stop старого агента, Rust пересобирать не нужно; start перед новым уровнем. Проверьте небольшой спуск, сбор и отсутствие дальнейшего падения, затем dump при ошибке. Для возврата к прежнему no_fall без спуска: underground=false перед следующим start (предварительно stop). При stop текущую высоту назад не телепортируем.

## Откат спуска после сообщения о сломанном финише

В report-1795212328498228820 уровень phase=1/unpaused, маски Hero остаются 4, gravity=0. Спуск timed_out: start_y=current_y=932.5623, target_y=996.5623. Этот дамп не доказывает достижение целевой глубины или причину несрабатывания финиша. Возможны несовпадение высоты с сенсором и отключённый mask=4 контакт. У финиша категория/ABI не определены; его срабатывание или выдача наград принудительно не вызываются.

Последний эксперимент `underground` **отключён по умолчанию**. no_fall, ×5, mask=4 и Candy auto возвращаются к режиму без преднамеренного начального спуска. Это откат возможной регрессии, не доказанное исправление контакта финиша; алгоритмы speed/masks/сбора не меняются. Старую высоту текущего героя код не угадывает и не восстанавливает.

Порядок: stop старой версии, обновление файлов, новый уровень/перезапуск игры при неясном состоянии, затем start перед входом. Rust пересобирать не нужно. Застрявший текущий забег такой сменой настройки не исправится автоматически. Если финиш всё ещё не работает в новом уровне без спуска, сохраните dump непосредственно у финиша до stop: следующий шаг — идентифицировать его сенсор/фильтр и штатное условие завершения, не отключать защиты или подменять награды.

## Ручной тест подъёма и возврата перед финишем

Новые команды требуют **cargo build --release** после обновления и перезапуска TAS:

- `catacombs above`: ставит запрос на подъём на 768 object-единиц (около 12 клеток) от высоты при первом ручном подъёме этого тела/запуска. Это относительная высота, не обнаружение границ карты. Повторный above не накапливает смещение.
- `catacombs return-height`: возврат к запомненной исходной Y; используйте **заранее перед финишем**, а не stop вместо возврата. Без previous above команда отклоняется.

Никакой автоматический подъём на старте не включён: underground по-прежнему false. Команды обрабатываются в существующем preventFall на текущем update с прежними Hero/physics/lock/phase/pause проверками. Движение через VY (вверх отрицательный, вниз положительный, максимум 8 physics/с с замедлением у цели), gravity=0, без записи transform/sweep/Hero.xy и без новых native ABI. Допуск достижения 4 object-единицы. Срок движения 3с wall-clock, без автоматических повторов при timeout; ожидание запроса до 5с и привязка к адресу state. Ручной return может заменить ещё выполняемый подъём. При паузе работа не выполняется, но wall-clock срок идёт. Новая команда заменяет предыдущий ещё pending запрос.

В no_fall.altitude смотрите mode/status(moving/reached/timed_out)/origin_y/target_y/current_y, отдельно altitude_pending и altitude_error. Старый неуспешный спуск через VY показал, что игра может сбрасывать вертикальную скорость: этот тест **не гарантирует фактический подъём**, timeout нужен именно для выявления такого случая. Если reached нет, пришлите dump, не пытайтесь бесконечно увеличивать значения. Полная защита от ловушек, достижение высоты над всей картой и работа финиша после возврата ещё не подтверждены.

Порядок: stop старого модуля, обновить и пересобрать Rust, новый TAS, start перед новым уровнем. В уровне above, status, затем заранее return-height и проверка reached до финиша, dump до следующего start. Stop отменяет pending и обнуляет вертикальную скорость/восстанавливает gravity по прежним guard-проверкам, **но не возвращает высоту автоматически**. При потере исходного тела/cleanup после перезапуска скрипта исходная высота не угадывается. При застревании перезапустите уровень/игру. README не менялся.

## Текущий режим: start заранее включает подъём на 30 клеток

`altitude_test.auto_rise=true`, `up=1920` (30×64 object-единиц), `timeout_ms=6000`. Теперь достаточно `catacombs start` **до входа в уровень**: модуль без ограничения времени ждёт активный неприостановленный Hero и успешное применение mask=4/no_fall, затем один раз задаёт цель startY−1920. Это не RPC-команда с 5-секундным expiry: ждать открытия уровня можно дольше. В start/status сразу видны auto_rise_enabled/altitude_offset, даже когда calls=0.

Автоподъём использует тот же ограниченный VY (максимум −8 physics/с), а не неизвестный teleport ABI или прямую запись Hero/physics координат. Поэтому подъём **не мгновенный**: примерно 2.4с плюс замедление у цели, если игра допускает такой VY. Движение/контакты во время подъёма продолжаются. Если игра сбрасывает скорость, no_fall.altitude станет timed_out; повторов в той же фазе/для того же fallBackup нет. Статус reached означает достижение относительной Y, не доказательство нахождения выше всех объектов карты.

Повторные кадры/ручной return не меняют origin и не запускают автоподъём заново. Наблюдаемый выход из phase=1 с успешным cleanup, новый state/тело или новый start могут подготовить следующий забег. Сохраняются прежние ограничения при скрытой смене уровня/потере callbacks. Underground остаётся выключен.

Ручной above сохранён и теперь тоже использует высоту 1920 от запомненного origin; команда больше не нужна для запуска первого подъёма. **Перед финишем по-прежнему нужен catacombs return-height**, затем проверка reached. Автоматического определения финиша/возврата нет. Stop обнуляет VY и пытается восстановить настройки, но не возвращает высоту.

Обновите JS/карту после stop старого модуля, stop/start перед новым уровнем. Rust пересобирать не требуется, если уже собрана версия с above/return-height. Включать start посреди уровня можно, но origin будет текущая высота, а не настоящий старт. Проверьте реальный подъём и возврат, при timed_out/неработающем финише сохраните dump до нового start. Рабочие ×5/masks/Candy auto не менялись; гарантии защиты от ловушек нет.

## Обычная скорость и проверка предложенных spawn-функций

По запросу пользователя speed_test.multiplier теперь **1**: проверенный базовый float движения остаётся ≈2.2, ускорение ×5 выключено. Перед обновлением выполните stop старого агента, чтобы он восстановил свой оригинал после ×5; если старый скрипт уже принудительно выгружен с изменённым float, перезапустите игру. Никакие фиксированные адреса старого процесса для восстановления не используются. Подъём на 30 клеток, noclip, no_fall и перенос существующих Candy сохранены.

**Непрерывный цикл спавна золотых ещё не реализован.** Пользовательские RVA 0x15EEA70 (factory), 0x15FB8A0 (spawn wrapper) и 0x1092110 (array push) пока не подтверждены runtime-кодом этой сборки/ABI/ownership. Даже при принятом допущении об отсутствии серверных проверок ошибочная регистрация в массиве может повредить процесс. Исчезновение объекта из массива не само по себе означает зачтённый подбор. Не вызываем эти функции, не создаём объект-копию, не меняем rarity существующего предмета и не увеличиваем счётчики. Ранее предложенная 0x1618980 не используется для Candy-body: её принадлежность оставалась неподтверждённой.

Добавлена **явная read-only** команда `catacombs spawn-probe` (требуется пересборка Rust `cargo build --release` для новой CLI-команды). RPC ставит запрос, следующий update onLeave проверяет свежий state/RTTI/active/unpaused/expiry5с. Снимаются ASLR-relative bounded окна: factory 768байт, wrapper384, push768, до256 инструкций на каждую цель, в пределах прежнего общего кэша40 целей/модуля/executable-readable памяти. Код не вызывается, прямые/косвенные цели не обходятся рекурсивно. Окна могут включать соседние функции, не заявляется полный CFG/ABI. При попадании ранее закэшированной цели используется существующее окно с его window_bytes, ошибок чтения/декодирования не скрываем.

В dump добавляется spawn_probe с candidate targets/bytes/disassembly и abi_verified=false/spawn_enabled=false. Status содержит только spawn_probe_status/pending, не тяжёлый код. По умолчанию до команды probe ничего не собирается, объекты/графы не дублируются; после запроса dump временно увеличится на эти три окна, но не на каждый кадр. Captured означает завершение обхода корней, каждый code/error проверяется отдельно. Stop отменяет queued запрос. Новая install очищает результаты.

Для следующего шага: stop старого модуля, обновление/пересборка/перезапуск TAS, start, активный уровень, `catacombs spawn-probe`, дождаться следующего update и `catacombs dump` до следующего start. Пришлите полный JSON без ручной обрезки. По коду проверим factory/body/scene/array-refcount и затем выберем контролируемый одноразовый spawn до непрерывного режима. Сейчас новый золотой на месте подбора не появится. README не менялся.

### Расширение spawn-probe после report-1795216187977739319

Код 0x1092110 показал indexed assignment: rdx — индекс, +0x18 — allocated slots, +0x20 — highest index, +0x28 — live counter, +0x30 — growth parameter, +0x38 — policy byte; запись заменяет старую ссылку и повышает refcount новой. Это ещё не доказанный append ABI/ownership. count+1 не используется. Factory/обёртка подтверждены по коду, но world/parent attachment остаётся открытым.

Тот же `catacombs spawn-probe` теперь дополнительно снимает:
- init-кандидат 0x15E90D0, до1536байт/256инструкций;
- текущий ZArray RTTI `6ZArrayI12KTGameObjectE`, capacity u64 (без небезопасного округления JS), highest s32, live/growth u64, policy u8;
- полный bounded обход не более1024 слотов: observed_live/candy_count, до16 примеров свободных индексов, сравнение live_counter_matches;
- один живой Candy с refcount/rarity/body/position и **фактический target текущего vptr+0x300** с кодом до768байт/256инструкций. Метод не вызывается.

Чтобы автосбор не успел удалить все Candy до ручной команды, в существующем 500мс sample один раз на адрес state сохраняется первый доступный снимок массива с живым Candy. Он выдаётся только как spawn_probe.early_array после явного запроса; текущий массив — spawn_probe.array. Это историческое свидетельство, не набор указателей для будущих вызовов: сохранённые адреса не разыменовываются из report/RPC. Ошибки/отсутствие Candy отражаются отдельно. Начинать start лучше до входа в новый уровень; если ни одного живого Candy не удалось застать, нужен новый забег.

Обновите JS/карту, пересборка не нужна при уже собранной spawn-probe CLI. Start перед новым уровнем, в активном уровне spawn-probe, через update dump до следующего start. Формат остаётся ограниченным четырьмя фиксированными кодовыми окнами и одним attach-методом (в общем кэше40), без дублирования по кадрам. Это read-only этап: новый золотой/непрерывный respawn ещё не реализованы. Обычная скорость ×1, noclip/подъём/автосбор существующих предметов не менялись.
