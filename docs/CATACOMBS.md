# Catacombs: диагностический модуль

Отдельный модуль в `catacombs/`, выключен по умолчанию. Это **наблюдение, не автосбор**: он не меняет память, не вызывает игровые функции, не отправляет запросы и не отключает ловушки.

## Запуск

Из корня проекта после обновления:

```sh
cargo build --release
./start/start.sh
```

В меню TAS:

```text
catacombs start
catacombs status
catacombs dump
catacombs stop
```

`start` загружает карту `memory/offsets.js` и устанавливает пять целевых хуков и один контрольный хук героя. Для каждой сигнатуры требуется ровно одно совпадение в исполняемых диапазонах библиотеки; RVA fallback не используется. Неоднозначность, ошибка установки или исключение чтения/проверки поля отключают все хуки. Причина доступна в `status` и отчёте. После ошибки можно повторить `start`; после изменения профиля выполните `stop`, затем `start`.

`dump` сохраняет `logs/catacombs-report.json` (перезаписывает предыдущий отчёт). Отчёт исключён из автоматической очистки logs при старте TAS; перед новым dump сохраните нужную предыдущую копию. `dump` нужно выполнить **до `stop`**, поскольку stop выгружает агент вместе с буфером. Отчёт содержит адреса текущего процесса и наблюдения, а не полный дамп памяти.

При штатном выходе модуль снимает хуки до отсоединения сессии. События не печатаются каждый кадр; статус проверяется командой.

## Что записывается

- Уникально найденные адреса пяти функций из предоставленного статического анализа.
- Снимок ReplayState и вектора дескрипторов после спавна и не чаще раза в секунду при update. Контейнер `+0x138` пока записывается только как непрозрачный указатель: его устройство неизвестно.
- Переходы байта активности DeathSkull, адрес объекта и vtable. Это **не доказательство зачтённого подбора**.
- Вход/выход addSkulls: необработанный целочисленный аргумент, локальные count/cap после штатного вызова.
- Факт вызова билдера CollectSkulls. Аргументы запроса и ответ сервера не декодируются.

Вектор ограничен 512 элементами, буфер — 1000 событиями, таблица черепов — 512 адресами. Старые записи вытесняются. Указатели не используются для последующей записи; снимки читаются из аргументов текущих вызовов. Профиль считается **кандидатом из статического анализа**, а не подтверждённой совместимостью. Даже уникальная AOB не доказывает правильность класса или смещений. ReplayState не является независимым признаком Catacombs.

## Первый эксперимент

1. Включить `catacombs start` перед входом в событийный забег.
2. Войти в Catacombs, проверить `catacombs status`.
3. Собрать один череп обычным способом, сделать `catacombs dump` и сохранить копию отчёта с пометкой времени.
4. Пройти забег штатно, повторить dump и сохранить вторую копию.
5. Передать оба отчёта и описание действий. Если модуль отключился — передать отчёт с `last_error`; не подбирать адреса вслепую.

Это начальная диагностика, не автоматическое получение всех недостающих данных.

## Что ещё нужно для полноценного модуля

1. Надёжный отличительный признак Catacombs, не просто ReplayState со списком.
2. Проверенные getter/setter позиции DeathSkull и ABI, владение/удаление объектов, раскладка контейнера.
3. Подтверждённый контакт подбора и изменение счётчика результата после него. Сейчас наблюдаем визуальный флаг и финальное начисление, но не сам контакт.
4. Проверенный SetTransform/аналог для тела героя и координатная система. Противоречивые скорости `+0x10/+0x11/+0x12` из отчёта не применялись: текущая карта TAS сохранена.
5. Список fixture, поля category/mask/group и категории ловушек/стен/сенсоров либо обработчик урона. Проверить сохранность подбора и триггера финиша.
6. Условие и зона штатного финиша, связь с результатом уровня. Адрес внутри функции нельзя вызывать как обычную функцию без анализа.
7. Проверка штатного ответа сервера и сохранения награды после перезахода. Наличие запроса не доказывает конкретную античит-проверку; отчёт этого модуля серверный ответ не содержит.

Ничто из этого не гарантирует совместимость после обновлений. При изменении игры профиль и наблюдения нужно перепроверять. История изменений: `docs/CHANGELOG.md`.

## Если start не отвечает

Обновите код и обязательно выполните `cargo build --release`: исправление доставки RPC находится в Rust, одной замены JS недостаточно. Обработчик сообщений регистрируется до загрузки агента; JS-ошибки печатаются как `ERROR catacombs agent`.

Ожидание install ограничено 30 секундами, status/dump — 5 секундами. Ctrl+C отменяет ожидание ответа и возвращает управление обработчику команды; при ошибке первой установки скрипт выгружается. Это отмена ожидания на хосте, не откат уже выполненных JS-операций. Нативные операции load/unload Frida остаются синхронными, их зависание при потере транспорта этот тайм-аут не покрывает.

При сбое пришлите вывод от `catacombs: scanning signatures` до ошибки. Не вводите dump, пока предыдущая команда ещё не вернулась в меню.

### Уточнение профиля ReplayState

В предоставленном дампе по RVA `0x13EF310` инструкция после первого call — `48 8B BB 60 01 00 00` (`mov rdi, [rbx+0x160]`). Сигнатура исправлена с ошибочного `83` на `BB`; rel32 call остаётся wildcard. Совпадение с фрагментом подтверждено тестом, глобальная уникальность проверяется только при запуске.

База `_ZTV11ReplayState` из отчёта `0x20090F8` включает заголовок Itanium ABI (offset-to-top и typeinfo). Для данной таблицы массив функций начинается по `+0x10`, слот 22 расположен по `0x20091B8`. В runtime объектный vptr обычно уже указывает на address point, поэтому повторно прибавлять заголовок к vptr нельзя. Диагностический модуль сейчас находит функции по AOB, не через эти адреса.

### Уточнение CollectSkulls

По предоставленной проверке старый 44-байтный пролог билдера CollectSkulls совпадал с 25 функциями. Теперь профиль использует 117 байт от начала функции по RVA `0xE4E650` до `45 89 7C 24 18`, с wildcard на rel32 трёх прямых вызовов. Пользователь подтвердил уникальность по своей библиотеке; модуль по-прежнему проверяет её при каждом включении. Длинная сигнатура не гарантирует совместимость с будущими обновлениями.

В присланном дизассемблере обычный `ret` расположен по `0xE4E6F4`; участок `0xE4E714` — call в exception path, не ret. Он не входит в выбранную сигнатуру.

## Контроль вызовов, если отчёт пустой

После обновления выполните `catacombs stop`, `catacombs start`. Не запускайте record/play параллельно этому эксперименту: установка других хуков на ту же функцию может изменить её пролог и помешать поиску по AOB. Если контрольная сигнатура уже пропатчена прежним запуском TAS pump, перезапустите игру и TAS и включите диагностику до record/play.

Сначала зайдите в обычный уровень, двигайтесь несколько секунд, сделайте dump и сохраните копию. Не выключая модуль, войдите в Catacombs, соберите один череп, сделайте второй dump. Контрольный хук использует общую `tas.signatures.FRAME_FUNC`, только уникальное AOB-совпадение, без fallback. Он не обещает получать именно игровое состояние: аргумент считается кандидатом на объект героя, его RTTI нужно проверить.

`counters` теперь содержит явные нули и число входов `hero_control`, `replay_update`, `skull_spawn`, `death_skull_update`, `skull_commit`, `collect_request`. Они увеличиваются **до** чтения кандидатных полей. Старые агрегаты frames/requests сохранены для совместимости. При отключении модуля новые входы уже не учитываются.

`last_hero` и события `hero_control` содержат адрес объекта, vptr, typeinfo и ограниченное 128 байтами имя RTTI; снимки берутся не чаще раза в секунду. Itanium typeinfo читается по vptr−8, без прибавления заголовка к объектному vptr. Ошибка RTTI записывается в `rtti_error`, но не отключает контрольный хук. Последний снимок сохраняется отдельно от кольцевого буфера.

- Контроль работает в обычном уровне и Catacombs, а целевые счётчики нулевые: связь этих пяти функций с текущим событием не подтверждена.
- Контроль работает только в обычном уровне: в событии может быть другой класс/функция героя.
- Все счётчики нулевые: проверить перехват и выбранную контрольную функцию; это ещё не доказывает поломку Interceptor.
- Целевой счётчик ненулевой при ошибке чтения: факт входа подтверждён, перепроверять раскладку полей.

Автоматический поиск активного состояния или контактного обработчика пока не добавлен: контрольный отчёт нужен, чтобы выбрать следующий шаг без записи в память.
